A. ORIGINAL VULNERABILITY
================================================================================
Exact file:
    src/app/api/listings/owned/route.ts
Exact line(s):
    Line 32 (original numbering, before the edit), inside the exported POST handler:
        await db.update(ownedProxies).set({ locked: Boolean(locked) }).where(eq(ownedProxies.id, id));
Supporting context:
    Line 23: export async function POST(req: Request)
    Line 25: const sessionUser = await getSessionUser();
    Line 26-28: 401 guard when there is no session user
    Line 29-31: body parsed; `const { id, locked } = body;` then `if (!id) return ... 400`
    Line 32: the update
    Line 33-34: response re-selects rows scoped to sessionUser.id and returns { success, owned }
What was wrong:
    The UPDATE statement was restricted by the primary key ONLY. The predicate was
    `where "owned_proxies"."id" = <caller-supplied id>`.
    The handler correctly established WHO the caller is (line 25, `sessionUser`), and
    correctly used that identity everywhere ELSE in the handler:
        - line 33: `db.select().from(ownedProxies).where(eq(ownedProxies.userId, sessionUser.id))`
    but the single statement that MUTATES data (line 32) never referenced
    `sessionUser.id` at all.
    Consequently, once any authenticated user passed the 401 gate at lines 26-28, the
    `id` value taken directly from the request body (line 30) was applied as an absolute
    row selector against the whole `owned_proxies` table. There was no ownership
    condition to prevent selecting a row owned by a different account.
    This is a broken object-level authorization control (IDOR / BOLA class): the
    authorization decision was made for "is this caller logged in" but never for
    "does this caller own the object being modified".
Confirmation basis: this was read directly from the source file before editing, not
inferred. The original file content was read in full (46 lines) prior to any change.
================================================================================
B. ROOT CAUSE
================================================================================
Why the original update could affect another user's record:
1. The table does carry ownership. src/db/schema.ts line 244 declares the column:
        userId: integer("user_id").references(() => users.id).notNull()
   So the data model supports ownership scoping; the information was available.
2. The handler had the owner. src/lib/auth.ts lines 15-44 implement getSessionUser(),
   which returns an object containing `id` (line 30: `id: user.id`). The route reads it
   at line 25 as `sessionUser`, so `sessionUser.id` was in scope at line 32.
3. The update did not use it. Line 32 built its WHERE clause from a single predicate,
   `eq(ownedProxies.id, id)`, where `id` originates from the untrusted request body
   (line 30: `const { id, locked } = body;`).
4. `owned_proxies.id` is `serial("id").primaryKey()` (src/db/schema.ts line 243), i.e.
   a globally unique, monotonically increasing integer. A global identifier is NOT an
   ownership identifier. Matching on it alone identifies WHICH row in the entire table,
   not WHO is entitled to change it.
5. Therefore any authenticated caller who could supply (or guess/enumerate) another
   account's row id would cause `locked` to be written on that other account's record.
   The subsequent response (line 33) re-selected only the caller's own rows, so the
   attacker's returned payload showed their own list - which visually masked the
   cross-account write. The mutation and the read-back were scoped differently.
Net effect: authentication was enforced; authorization (object ownership) was not.
Note on failure mode before the fix: the original code did not throw, did not log, and
did not signal an error. A cross-owner update would report `success: true`. This is why
the defect would not surface in ordinary usage or in error monitoring.
