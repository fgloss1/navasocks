- exact file: src/app/api/user/keys/route.ts
- exact line(s): line 75
- what was wrong: The DELETE operation for API keys used only `eq(apiKeys.id, parseInt(keyId, 10))` in the WHERE clause, without verifying that the API key's userId matches the authenticated session user. - The DELETE handler obtained the session user via `getSessionUser()` but only filtered the delete by key ID. Since the `apiKeys` table stores `userId` referencing the creating owner, the missing condition meant no database-enforced barrier prevented a user from deleting another user's API key. - concise description: Added `eq(apiKeys.userId, sessionUser.id)` to the WHERE clause of the `db.delete()` call, using the `and()` combinator from drizzle-orm to combine two conditions. This ensures an authenticated user can only delete an API key when BOTH the requested ID matches AND the key's userId belongs to the current session user. The `and` import was added to the existing drizzle-orm import statement.

======================================================================

1. Ownership is enforced in the DELETE statement itself (atomic, no TOCTOU
   window, no pre-check SELECT needed):
     await db
       .delete(apiKeys)
       .where(and(eq(apiKeys.id, parsedKeyId), eq(apiKeys.userId, sessionUser.id)));
   -> SQL emitted (verified with drizzle toSQL()):
      delete from "api_keys" where ("api_keys"."id" = $1 and "api_keys"."user_id" = $2)
      params: [<requested id>, <session user id>]
   A row can only be removed if BOTH the requested key id matches AND
   user_id equals the currently authenticated session user.

   used, so the row that gets deleted always matches the id that was actually
   requested (this closes the parseInt coercion path in section B.2):
     const parsedKeyId = Number(keyId.trim());

Additional security findings - REPORTED ONLY, NOT FIXED (per requirement 5)
--------------------------------------------------------------------
1. src/app/api/user/keys/route.ts POST (line 44): API keys are generated with
   `Math.random()` (`nsk_live_` + 2x 10 base36 chars). Math.random() is not a
   CSPRNG and the output is predictable; key material must come from
   crypto.randomBytes / crypto.getRandomValues. (CWE-338)
2. src/lib/auth.ts getSessionUser (lines 18-26): the session cookie
   `nsocks_session` is the raw, unsigned user id. Anyone who can set a cookie
   can impersonate any account by supplying an arbitrary id, which defeats
   every object-level check in the app (including the one fixed here). A
   signed/HMAC or server-side session store is required. Fixing it would
   change authentication behaviour and login, so it was left untouched.
   (CWE-565 / CWE-384)
3. src/app/api/user/whitelist/route.ts POST (lines 18-22): when a
   `subscriptionId` is supplied, the UPDATE filters only on
   `eq(userSubscriptions.id, subscriptionId)` with no user check - the same
   IDOR pattern fixed here, in an unrelated route that I was told not to
   modify. (CWE-639)
4. src/app/api/user/keys/route.ts: the DELETE handler still answers
   {success:true} when the key does not exist or belongs to another user.
   I deliberately left the response contract unchanged (requirement 4) rather
   than adding a 404; the owner predicate in the WHERE clause is what enforces
   authorization.
5. src/app/api/user/keys/route.ts has no rate limiting on key creation or
   deletion, and GET returns full plaintext `apiKey` values to the client
   (stored unhashed, so a database leak exposes all keys directly). Not
   changed: out of scope for this object-level authorization task.
6. src/app/api/listings/owned/route.ts PUT (lines 41-46) still returns
   {success:true, persisted:false} with no database operation (pre-existing,
   already noted in the Challenge 1 report).
