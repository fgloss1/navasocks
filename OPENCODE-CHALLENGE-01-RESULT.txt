A. Original vulnerability
- exact file: src/app/api/listings/owned/route.ts
- exact line(s): POST handler, line 32 (original numbering); line 4 import line (original)
- what was wrong:
  - Line 4 (original): `import { eq } from "drizzle-orm";`
  - Line 32 (original):
    `await db.update(ownedProxies).set({ locked: Boolean(locked) }).where(eq(ownedProxies.id, id));`
  - The route required authentication (401 when no session user) and read the
    client-supplied `id`/`locked` from the JSON body, but the UPDATE's WHERE
    clause constrained ONLY the record id. It did not constrain the record to
    the current session user, even though `sessionUser` was available in scope
    and the GET handler plus the POST re-select both correctly filter by
    `ownedProxies.userId = sessionUser.id`.

B. Root cause
- Any authenticated user could send POST /api/listings/owned with an arbitrary
  `{"id": <victim record id>, "locked": <bool>}` body. Because the WHERE clause
  was only `owned_proxies.id = :id`, the database updated whichever row had
  that id, regardless of its `user_id` column. This is an object-level
  authorization (IDOR/BOLA) flaw: authentication was present, but ownership
  authorization on the write was missing. The subsequent re-select
  (`where(eq(ownedProxies.userId, sessionUser.id))`) only returns the caller's
  own rows, so the attacker does not see the victim's row in the response, but
  the victim's `locked` value has already been changed.

C. Change made
- exact file changed: src/app/api/listings/owned/route.ts (only this source file)
- concise description of the modification (2 lines, minimum change):
  - Line 4: `import { eq } from "drizzle-orm";` -> `import { and, eq } from "drizzle-orm";`
  - Line 32: `.where(eq(ownedProxies.id, id))` ->
    `.where(and(eq(ownedProxies.id, id), eq(ownedProxies.userId, sessionUser.id)))`
  - Effect: an authenticated user can now update ONLY the owned-proxy record
    that matches BOTH the requested record ID AND the current session user's id.
    A request for another user's record id matches zero rows, so no other
    user's record is modified. Route, HTTP method (POST), request format
    (`{id, locked}`), response format (`{success, owned}` / error shapes),
    GET/PUT behavior, UI, and the authentication implementation were preserved.
