A. ORIGINAL VULNERABILITY
--------------------------------------------------------------------------------
Any authenticated user could flip the `locked` flag on ANY other user's
`owned_proxies` row by supplying that row's numeric `id`.
Vulnerable code (pre-fix), src/app/api/listings/owned/route.ts line 32:

line 18
    32:    await db.update(ownedProxies).set({ locked: Boolean(locked) }).where(eq(ownedProxies.id, id));
The UPDATE predicate was scoped ONLY by primary key:
    where eq(ownedProxies.id, id)
The `id` value is fully attacker-controlled, taken straight from the request body
(src/app/api/listings/owned/route.ts lines 29-31):
    29:    const body = await req.json();
    30:    const { id, locked } = body;
    31:    if (!id) return NextResponse.json({ error: "Missing id" }, { status: 400 });
`sessionUser` WAS resolved and checked for presence (lines 25-28), so the endpoint
was authenticated, but the resolved identity was never used in the write
predicate. The only post-write read (line 33) was correctly scoped by
`sessionUser.id`, which made the bug easy to miss on inspection while the write
itself was unscoped:
    33:    const mine = await db.select().from(ownedProxies).where(eq(ownedProxies.userId, sessionUser.id));
    34:    return NextResponse.json({ success: true, owned: mine });
Impact: cross-tenant write. `owned_proxies.id` is a `serial` (sequential)
primary key -- src/db/schema.ts lines 242-244:
    242: export const ownedProxies = pgTable("owned_proxies", {
    243:   id: serial("id").primaryKey(),
    244:   userId: integer("user_id").references(() => users.id).notNull(),
Because IDs are sequential, an attacker does not even need to guess: ids 1..N can
be enumerated. The owning user is identified by `ownedProxies.userId`
(src/db/schema.ts line 244), which the vulnerable query ignored.
Reachability from the UI: src/app/dashboard/page.tsx lines 526-534 is the only
caller and sends `{ id: item.id, locked: !item.locked }`, confirming the request
format. The UI never exercised the unauthorized case, which is why the flaw was
latent.
--------------------------------------------------------------------------------
B. ROOT CAUSE
--------------------------------------------------------------------------------
Classic missing authorization predicate on a state-changing object reference
(CWE-639 / CWE-862).
Three contributing factors, all in the pre-fix source:
1. src/app/api/listings/owned/route.ts line 32 -- the UPDATE `where()` clause was
   built from the client-supplied primary key alone. Object ownership
   (`ownedProxies.userId`) was not part of the predicate.
2. src/app/api/listings/owned/route.ts lines 25-28 -- `getSessionUser()` was
   called and null-checked, which establishes authentication but not
   authorization. The resulting `sessionUser.id` was used only for the
   subsequent read (line 33) and the response, never to constrain the write.
3. src/lib/auth.ts lines 15-44 -- `getSessionUser()` returns a trustworthy
   server-side identity object (`id`, `role`, `status`, ...) derived from the
   `nsocks_session` cookie. The fix therefore needed no auth-layer change at
   all: the correct `sessionUser.id` was already available in the handler scope
   at line 25. The authentication implementation was left untouched as required.
Note the contrast with the correct pattern already used elsewhere in the codebase
for the same table, src/app/api/listings/owned/route.ts line 15 and line 33, and
src/app/api/user/keys/route.ts lines 21-25 -- all scope by `userId`. Line 32 was
the sole outlier.
--------------------------------------------------------------------------------
C. CHANGE MADE
--------------------------------------------------------------------------------
Single behavioral change: scope the UPDATE predicate to the session user's own
record by requiring BOTH the requested record id AND the session user's id.
Post-fix src/app/api/listings/owned/route.ts lines 32-35:
    32:    await db
    33:      .update(ownedProxies)
    34:      .set({ locked: Boolean(locked) })
    35:      .where(and(eq(ownedProxies.id, id), eq(ownedProxies.userId, sessionUser.id)));
Supporting one-token import change, src/app/api/listings/owned/route.ts line 4:
    4: import { and, eq } from "drizzle-orm";
(added `and` to the pre-existing `drizzle-orm` import on the same line)
Semantics after the fix:
- id belongs to the session user  -> exactly 1 row updated (unchanged happy path)
- id belongs to ANOTHER user      -> 0 rows updated, no state change
- no id                          -> unchanged, 400 "Missing id" (line 31)
Deliberately NOT changed, to preserve the contract:
- No new 403/404 response was introduced. A non-owned id simply matches 0 rows
  and the endpoint still returns the same `{ success: true, owned: mine }` body
  (line 37), which contains only the caller's own records. This keeps the
  response format byte-identical and leaks no information about the existence of
  other users' records.
- GET (lines 9-21), PUT (lines 44-49), the route path, the HTTP method, the
  request format, the `dynamic = "force-dynamic"` export (line 7), the error
  handling (lines 38-41) and all console logging are untouched.
- src/lib/auth.ts and src/db/schema.ts were read but not modified.
