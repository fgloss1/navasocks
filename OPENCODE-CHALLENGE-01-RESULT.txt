A. Original vulnerability
--------------------------------------------------------------------------------
File: src/app/api/listings/owned/route.ts

Vulnerable line (original line 32, inside the POST handler):

    32:    await db.update(ownedProxies).set({ locked: Boolean(locked) }).where(eq(ownedProxies.id, id));

Supporting line (original line 30, the attacker-controlled input):

    30:    const { id, locked } = body;

Supporting line (original line 4, import that lacked the `and` combinator):

     4: import { eq } from "drizzle-orm";

What was wrong:
The POST handler authenticated the caller (401 if no session, original lines 25-28)
but then scoped the UPDATE by primary key ONLY. The `WHERE` clause contained
`eq(ownedProxies.id, id)` and nothing else. `sessionUser` was used exclusively for
the follow-up SELECT (original line 33), never for the write. The record's owning
column `ownedProxies.userId` (src/db/schema.ts line 244) was never part of the
update predicate.

Result: any authenticated user could flip the `locked` flag on ANY row in
`owned_proxies`, including rows belonging to other users, by supplying that row's
numeric `id`. This is a classic broken object-level authorization (BOLA/IDOR)
write primitive. The response was always `{ success: true, owned: [...] }`, so
the cross-user write was silently confirmed as a success.

Confirmed from source (not assumed):
- src/db/schema.ts line 242-263: `ownedProxies` has `id` (serial PK) and
  `userId` (integer, NOT NULL, FK -> users.id) as two SEPARATE columns, so a
  two-predicate AND on both columns is both possible and correct.
- src/lib/auth.ts lines 15-44: `getSessionUser()` returns a trusted `id` taken
  from the session cookie's user lookup, and returns `null` for missing,
  non-numeric, banned, or suspended users. It is a sound identity source.
- src/app/dashboard/page.tsx lines 526-534 (read-only, NOT modified): the client
  `toggleLock` sends `POST /api/listings/owned` with body `{ id, locked }`.
  This confirms the request format that had to be preserved.

--------------------------------------------------------------------------------
B. Root cause
--------------------------------------------------------------------------------
The authorization check and the mutation were decoupled. The handler proved WHO
the caller was (`getSessionUser()` -> `sessionUser.id`) but then authorized the
write using a predicate built solely from attacker-supplied input (`body.id`).

`id` is a globally sequential `serial` primary key, not an unguessable token, and
it is fully attacker-controlled. Because the UPDATE predicate was a pure primary-
key lookup, the database had no way to know the caller did not own the row: the
ownership column `user_id` was not part of the WHERE clause. Any valid session
was therefore sufficient to mutate any user's `owned_proxies` row. Enumeration is
trivial because `serial` IDs are small and sequential, and the endpoint's response
body (`owned`) only ever reflects the caller's own rows, so the attack produced no
visible anomaly to the attacker or the victim.

The same pattern is a "confused deputy": the server holds the authoritative owner
value (`sessionUser.id`) but ignores it at the point of mutation, letting the
client assert which object to mutate.

H. Remaining concerns
--------------------------------------------------------------------------------
Findings discovered during the required inspection. Per instruction 5 these were
NOT fixed and are recorded only. Listed most to least severe.

HIGH - Session cookie is a plaintext, unsigned user ID (src/lib/auth.ts)
  `setSessionUser` (lines 56-65) stores the bare numeric user id in the
  `nsocks_session` cookie; `getSessionUser` (lines 15-44) trusts that integer
  directly and loads the account. Consequences:
    - No HMAC/signature/server-side secret: anyone who can set or edit the cookie
      becomes any user by guessing a small sequential id. Session forgery is
      trivial and requires no secret.
    - The 7-day `maxAge` is enforced by the browser only. The server never
      validates expiry, so a stolen or replayed cookie remains valid
      indefinitely, and there is no server-side revocation or rotation path.
    - The plaintext id also discloses the internal user id to the client.
  This is the root enabler that makes IDOR bugs elsewhere cheap to exploit. Fixing
  it would mean changing the authentication implementation, which instruction 4
  and instruction 6 explicitly forbid for this task.

HIGH - Two-factor secret stored in plaintext (src/db/schema.ts line 10)
  `users.twoFactorSecret` is a plain `text` column with no encryption-at-rest and
  no separate vault/KMS reference, unlike the `accessPasswordEncrypted` columns
  elsewhere in the schema. A database read or backup disclosure yields every
  user's 2FA secret. Out of scope (schema + auth change).

MEDIUM - Full owned_proxies rows are serialized to the browser
  GET (line 15) and POST (line 33) both `select()` with no column projection and
  return the entire row, which includes `accessPasswordEncrypted`,
  `providerCredentialRef`, `transportHost`, `transportPort`, and internal access
  host/port fields. Encrypted credential material and internal infrastructure
  topology are pushed to the client even though the dashboard only needs a small
  subset. Encrypting data does not help if the ciphertext is handed to the
  client. Recommend an explicit column allow-list in both handlers.

MEDIUM - Unused `users` import (src/app/api/listings/owned/route.ts line 3)
  `import { ownedProxies, users } from "@/db/schema";` - `users` is never
  referenced in this file. Harmless dead code, but it obscures which tables the
  route actually touches during review. Left in place to keep the diff minimal.

LOW - Ownership miss is indistinguishable from success (POST, line 32-34)
  After the fix, a request naming another user's `id` matches zero rows and the
  route still replies `{ success: true, owned: [...] }` with the caller's own
  list. This is not an authorization hole and, importantly, it leaks nothing: the
  response contains only the caller's own rows, so record-ID existence cannot be
  probed. Flagged only because the API cannot distinguish "toggled" from "no such
  record of yours". Returning 404/403 would change the documented response
  format, which instruction 4 forbids, so the status quo was kept deliberately.

LOW - No-op PUT handler on the same route (lines 41-46)
  `PUT` unconditionally returns `{ success: true, persisted: false }` and never
  reads the request or touches the database. It is misleading (always claims
  success) and is a candidate for confusion during incident review, but it
  performs no state change and is therefore not a vulnerability. Left untouched.

LOW - No CSRF token on the state-changing POST
  The endpoint mutates state and relies solely on cookie authentication. Risk is
  substantially reduced by `sameSite: "lax"` (src/lib/auth.ts line 62), which
  blocks the cookie on cross-site subresource POSTs, and the handler requires a
  JSON content type that a cross-origin HTML form cannot produce. Explicit
  origin/CSRF-token checking would still be defense in depth.

INFO - Schema-level observations (src/db/schema.ts), not changed
  - `ownedProxies.userId` (line 244) has no `onDelete` rule, so user deletion can
    orphan proxy rows, unlike `supportTickets.userId` (line 267) which cascades.
  - `proxyListings.ownerUserId` (line 235) is a nullable integer with no foreign
    key to `users.id`, so listing ownership is unconstrained by referential
    integrity.
  - `ownedProxies.listingId` (line 245) is likewise an unconstrained integer
    with no FK to `proxyListings.id`, so owned rows can point at listings that no
    longer exist.
  - `userSubscriptions.proxyPassword` (line 49) is a plaintext credential column
    whose sibling rows in other tables use `...PasswordEncrypted`; the naming is
    consistent with plaintext storage.
