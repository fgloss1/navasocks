    ...
    const API_KEY_ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyz";
    // Cryptographically secure replacement for the previous non-cryptographic
    // pseudo-random generator. Bytes at or above the largest whole multiple of the
    // alphabet size are discarded so that every character stays equally likely
    // (no modulo bias).
    function secureApiKeySegment(length: number): string {
      const limit = 256 - (256 % API_KEY_ALPHABET.length);
      let segment = "";
      while (segment.length < length) {
        const bytes = randomBytes(length);
        for (let i = 0; i < bytes.length; i++) {
          if (bytes[i] >= limit) continue;
          segment += API_KEY_ALPHABET[bytes[i] % API_KEY_ALPHABET.length];
          if (segment.length === length) break;
        }
      }
      return segment;
    }
    ...
    // in POST, replacing the old Math.random() template literal:
    const newKey = `nsk_live_${secureApiKeySegment(10)}${secureApiKeySegment(10)}`;
Why this is correct and minimal:
  - `randomBytes` is a CSPRNG (OS entropy, /dev/urandom or BCryptGenRandom),
    so key material is no longer predictable;

    252, and 252 = 36 * 7) makes all 36 characters exactly equally likely -
    a plain `% 36` over 256 bytes would have biased the first 4 residues;

    `nsk_live_` prefix is byte-for-byte identical, the alphabet is identical
    ([0-9a-z]), and the random part is the 20-character case that the old
    generator produced 98.5% of the time (now consistently, which is the
    closest stable match to the original structure/length);
  - entropy per key is 20 * log2(36) = 103.4 bits of CSPRNG output.

A. Original Vulnerability
======================================================================
Class: Use of Insufficiently Random Values for a Security-Critical Value
      (CWE-338 / CWE-330), key material derived from a non-cryptographic PRNG.
The API-key creation logic in POST /api/user/keys generated the secret part of
the key with `Math.random()`. Baseline line (pristine copy of this project):
    const newKey = `nsk_live_${Math.random().toString(36).substring(2, 12)}${Math.random().toString(36).substring(2, 12)}`;
`Math.random()` is a fast, non-cryptographic PRNG (V8: xorshift128+ with a
per-context 128-bit state). It is not a CSPRNG, its output is not
forward-secure, and its internal state is recoverable from a handful of
observed outputs, so keys generated this way are predictable to an attacker who
can observe any of them. The value is then persisted as a live API credential
(src/db/schema.ts, `apiKeys.apiKey` text NOT NULL UNIQUE) and returned to the
client, so predictability translates directly into account takeover of every
API integration of the victim.
Measured behaviour of the original generator (200,000 samples, this machine):
  - random-part length: 20 chars in 98.5% of keys, but 17 (3), 18 (93) and
    19 (2,947) chars otherwise - i.e. the key length was not even stable;
  - the base-36 fraction of an IEEE-754 double is truncated by
    `substring(2, 12)`, so each segment carried at most ~52 bits of the
    PRNG's 128-bit state, and very small doubles produce degenerate segments
    (verified: (1e-20).toString(36).substring(2,12) === "0000000000", i.e. an
    all-zero key segment);
  - charset was base36 lowercase [a-z0-9] in all 200,000 samples, which is why

Related weaknesses observed - REPORTED ONLY, NOT FIXED (requirement 6)
--------------------------------------------------------------------
1. API keys are stored and returned in PLAINTEXT (`apiKeys.apiKey` is a plain
   text column and GET returns the full key value). Standard practice is to
   store only a hash (e.g. sha256) and show the secret once at creation, so a
   database leak does not yield usable credentials. Fixing this would change
   the key storage/lookup design, which this challenge explicitly forbids.
2. There is no rate limiting on key creation/deletion and no way to scope or
   expire a key (no last_used_at update, no expiry column usage) - out of scope.
3. Other `Math.random()` uses in the project remain insecure and were left
   untouched on purpose: src/app/api/proxies/generate/route.ts (lines 81, 85 -
   generates proxy session ids/usernames), src/app/api/proxies/test/route.ts
   (lines 10, 46 - timing jitter and random test IPs), and
   src/app/api/auth/forgot-password/route.ts (lines 23, 39 - mock reset token).
   Of these, the password-reset mock token is the one I would prioritise next;
   it is explicitly out of scope for this challenge.
4. src/lib/auth.ts: the session cookie `nsocks_session` is the raw, unsigned
   user id, so a cookie can be forged to impersonate any account, which would
   bypass the API-key ownership check added in Challenge 2. Authentication
   behaviour must stay unchanged for this task, so it is reported only.
   (CWE-565 / CWE-384)
5. src/app/api/user/whitelist/route.ts lines 19-22 still contain the same
   IDOR pattern fixed in Challenge 2 (update filtered only by
   `eq(userSubscriptions.id, subscriptionId)` with no owner check) - unrelated
   route, reported only. (CWE-639)
