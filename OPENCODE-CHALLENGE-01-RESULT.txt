What was fixed
W1 — unsigned raw-ID cookie. nsocks_session held userId.toString(); getSessionUser() did parseInt(cookie.value, 10). Any integer authenticated as that user with no password, and logout revoked nothing. Now a 256-bit randomBytes token goes in the cookie and only its SHA-256 hash goes in the database.

W2 — password reset was account takeover. The route destructured { email, username, newPassword } — the resetToken the page sent was never read. Any username plus a 6-char password reset that account, unauthenticated, including admin. Now a valid, unexpired, single-use, server-stored token is mandatory, and a reset revokes all sessions.

W4 — 2FA was decorative. Any 6 characters passed, no TOTP was ever computed, and every user shared the hardcoded secret JBSWY3DPEHPK3PXP — the public example value printed in RFC 6238. Now real RFC 6238 TOTP with per-user 160-bit CSPRNG secrets, verified constant-time.

Two things worth your attention
A lockout I introduced and then fixed. src/db/seed.ts seeded the admin with the shared demo secret. My first login implementation correctly refused it — which meant the seeded admin could never log in, since re-enrolling requires being logged in, and seedDatabase() only runs on an empty users table. I fixed the seed and added a self-heal that clears the unusable 2FA state and lets the password login through. Section 5 of the report argues why clearing is not a weakening: anyone with the password already passed 2FA with any 6 digits, so that control protected nothing. A deliberate deviation from "smallest change": getSessionUser() updates last_used_at at most once per 5 minutes rather than per request, because it runs inside a server component render and a write per request for an informational field is not worth it.
